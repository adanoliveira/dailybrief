# DailyBrief - AI RSS Digest – Functional Specification  

DailyBrief – a PWA news reader that lets people pick topics, publications, and regions then delivers AI-summarised articles and a "Yesterday's Stories" digest.


DailyBrief is an AI news reader (mobile web app with SPA features) that pulls news from New API (https://newsapi.org/) hourly and presents them to user:

- with an article abstract at the top, generated by visiting the news link and that presents the gist of the news, allowing the user to skip the full read. Or to judge if they want to move further to read the full article

- a daily digest generated every morning based on previous day's news: filtering all the articles from topics and publishers the user follows, a news article-like digest is generated every moning and made available to the user, where they can check the main stories from the previous days with most relevant sources for deep dive, it wanted.

Although this app can turn into a major News Aggregator, we will start with an simple web based POC MVP, so that I can use it as my final project for the cs50 web course and use it to validate demand and start getting feedback from users.

The final version will likely be composed of native mobile apps that aggregate and summarize news from tradional mainstream news outlets, as well as modern sources of news that use the RSS protocal: blogs (wordpress, substack, medium), podcasts, social media (youtube, instagram, x.com, reddit) and others.

Our purpose is to be a "neutral", user-controlled news feed for the web. We will aggregate mainstream news providers, podcasts and other content creators the user want to follow in a simliar fashion to a tradicional RSS reader. The goal here is to be clean news feed for consuming news in a focus and unbiased way. Without the infinite scroll, polarity and ads from social media. The user should be productive and informed by using our product.

Our MVP however will be SPA-like web app centered around mainstream news sources available through News API, mobile-first, built with modern architectures:
- modular monolith for the backend, accessible through a secure REST API
- mobile first UI and functionalities, allowing uers to add the web app to their smartphone home screen, read news offline and receive notifications
- modern front-end using next-js, react and shadcn/ui

We will aim to: **ship in 1 week** an MVP that

- Let's the user select their news preferences, by selecting topics, regions, publishers of interests. And which languages they would like to consume the news in.
- Based on their preferences, shows a custom ranked feed with article-level AI summaries, and a daily digest of the previus day's top stories within their interests (top 3-5 merged stories with source links deep dives).
- Also shows a unfilted top headlines from around the world to also provide an unfiltered and unbsiesed view.
- Works great on mobile and is installable (PWA).
- Frictionless authentication and long session times for easy access. Auth with Google, Apple, or email magic-link – no passwords.
- Will be hosted on Vercel, both the front-end and the back-end
- Will be multi-lingual by design, to work for readers around the world, infering their prefered app language based on their location, but enabling it to change. The app language is detached from the news articles languages: the user can select news from any language independently. The languages they choose for reading will not be translated to their app language, all other article languages will be translated.
- Meets the CS50-Web rubric (Django back-end, JS front-end, responsive design, README + video).
- "Done" = a 3-minute demo flows smoothly through onboarding → feed → article summary → digest.

### Views / Screens
The app would have the following views (mobile first):

#### Authenticated Users
* **onboarding flow**: after sign up, the user would be forwarded to a full page (or full modal on desktop) wizard to setup their news preferences, choosing (from the options available or top 20 most popular): 
- topics of interest (al least 1), 
- region of interest (at least 1), 
- publishers (optional) and 
- news languages (optional, default to the one infered by the user's location, but can change and select up to 3). 

After that, the user is directed to their custom news feed (home):

* **home**: the custom news feed for the user, where they see the news based on their preferences. - Up top, there's a action bar (filtering, searching, sorting, view options). And a corresponding search and filtering UX flow on modals. 
- The first article shown is the daily digest, from news of the previous day. There should be a state "your daily brief is being generated" for when the backend is still working on the first news digest. Once the user clicks on the digest, the previous days' digest is presented, where a user can see navigate back to their home. A link for a list of past digests ("see all digests" or something like that) is visible as a secondary action link in the digest card at the top of this home.
- At last, there's the list of articles filtered based on the user's preferences, ordered from lastest to oldest by default.
- This should be the default "/" route for authenticated users.

* **world**: similar to the home, it's a feed but for unfiltered news, based on top headlines from  all around the world or the region the user follows. Here, no daily digest is presented

* **article**: this view is for each article pesented. Just below the article headline, there should be an abstract for this article and then the full regular content returned from the news feed (link, article summary, or full article). Add a CTA for 'read the full article or story' or another copy like that.

* **profile**: this is the view for the user account. They should find a preferences section, where they can change their article filtering prefenreces (for their custom home feed). The preferences should be edited in modals for full control of options, instead of inline (with limited space). The home feed should be updated immediately after preferneces changes. They can also change their account data here and sign out. 

#### Un-authenticated Users
* **home, marketing website**: consisting of a short "hero" section that gives a gist of the app, with a heading, subheading, image (or gif, video), and CTA to "create your custom news feed". Below the hero section, we present content as in the world section for authed users descibred above: with top headlines and filtering options, to give users a taste of the app. We should load  limited amount of news articles (e.g. 100 at most) so that this page remain performant. This should be the default page "/" for unauthenticated users.

* **auth flow**: a regular auth flow with sso (google at first) and email sign up, with a otp or magic link, without password.

We use a hybrid approach to auth, involving both the front-end (next-auth + prisma) for low-latency and ease of implementation and the back-end:
Frontend auth flow
1. User authenticates with NextAuth
2. On successful login/registration, make API call to Django
3. Create or update corresponding Django user record
4. Store Django user ID in NextAuth session data

Backend access control
1. Frontend sends NextAuth session token with API requests
2. Django validates token using a shared secret or public key
3. Maps the authenticated user to Django user

More details in docs/diagrams/auth-flow.md

## 3. Architecture and Tech Stack

We implement a **domain-driven modular monolith** to make our project easier to divide into services if growth demands it, while maintaining clear separation of concerns and bounded contexts.

### Modular Monolith Architecture

Following DDD principles, we organize our system into **three core domains**:

#### 1. **Sources Domain** (Integration Layer)
**Responsibility:** Fetch article metadata from external sources
- **`newsapi/`** - NewsAPI integration for mainstream news outlets
- **`feeds/`** - RSS feed processing for blogs and independent sources  
- **Future:** YouTube, podcast, and social media integrations

#### 2. **Content Domain** (Processing Layer)
**Responsibility:** Enhance articles with full content and AI analysis
- **`content/fetcher/`** - Web scraping for full article content with robust error handling
- **`content/summariser/`** - AI-powered summarization and analysis
- **`content/analyzer/`** - Content classification, entity extraction, and enrichment
- **Future** classifier (Topic/sentiment classification), translator (Multi-language support)

#### 3. **Articles Domain** (Repository Layer)
**Responsibility:** Manage article lifecycle and state
- **`articles/`** - Central content repository with processing state tracking
- **Content availability states:** Handle paywalls, access restrictions, and processing failures
- **Fallback strategies:** Graceful degradation when full content unavailable

### Content Availability & Processing Pipeline

Our architecture addresses real-world challenges:
- **Paywalls & Access Restrictions:** Intelligent detection and fallback strategies
- **Technical Failures:** Robust retry mechanisms with exponential backoff
- **Content Quality:** Assessment and enhancement of extracted content
- **Processing States:** Comprehensive tracking from fetch to AI enhancement

### Decoupled Frontend & Backend
- **Back-end:** Django/Python with domain-specific apps communicating via service classes
- **Front-end:** Modern React/Next.js SPA with graceful content availability indicators
- **Integration:** Clean APIs with content status awareness for optimal UX

### Supporting Infrastructure
- **Background Processing:** Celery for async content fetching and AI processing
- **AI Integration:** OpenAI and Anthropic with provider-agnostic architecture
- **Monitoring:** Comprehensive tracking of content availability and processing success rates
- **Multilingual Support:** Native support with content translation capabilities

Our whole application will be deployed to Vercel, for simplicity, initially. In the future, we may consider hosting the back-end on another cloud provider.

### Docker Development Environment

To facilitate consistent development and testing, we've implemented a containerized development environment using Docker. This approach ensures that all team members work with identical dependencies and configurations, reducing "it works on my machine" issues.

### Docker Architecture

Our Docker setup consists of the following services:

1. **Backend (Django)**: A Python container running Django with a modular monolith architecture.
2. **Frontend (Next.js)**: A Node.js container running Next.js with React and shadcn/ui.
3. **Database (PostgreSQL)**: A Postgres database container for data persistence.
4. **Redis**: Used by Celery for task queueing and results backend.
5. **Celery Worker**: For background tasks like news fetching, summarization, and digest generation.
6. **Celery Beat**: For scheduling recurring tasks.

### Configuration Details

- **Modular Structure**: The backend uses a modular monolith approach with Django apps organized in an `apps` package.
- **Python Path Management**: We set `PYTHONPATH=/app` in the container to ensure proper module imports.
- **Volume Mounting**: 
  - Development files are mounted as volumes to support hot-reloading.
  - Node modules are handled with anonymous volumes to prevent overwriting.
- **Dependency Management**: npm with `--legacy-peer-deps` flag to handle dependency conflicts in the frontend.
- **Network Configuration**: All services are on the same Docker network, with appropriate port mapping to the host.

### Development Workflow

Our Docker setup supports an efficient development workflow:

- **Hot Reloading**: Frontend code changes are automatically detected and applied without container rebuilds.
- **Database Migrations**: Run inside the backend container using Django's migration system.
- **Command Execution**: Use `docker-compose exec` to run commands in running containers.
- **Logs**: Monitor service logs with `docker-compose logs -f [service]`.

### Rebuilding Requirements

Container rebuilds are only necessary when:
1. Adding or updating dependencies in package.json or requirements.txt
2. Modifying Dockerfiles or docker-compose.yml
3. Changing container environment variables

This Docker setup provides a consistent environment across development, testing, and (potentially) production, ensuring that our modular monolith architecture remains maintainable and scalable.

Our app/brand is called "DailyBrief" or dailybrief. We can initially use svg logo files in `docs/brand/logo` to generate logo variations for our brand (dark, white, favicon).

### Theme Implementation

DailyBrief has implemented a fully functional dark/light theme system using:

1. **next-themes**: Manages theme state, persists user preferences, and handles system preference detection
2. **Tailwind darkMode**: Set to `["class"]` in `tailwind.config.ts` to enable class-based dark mode  
3. **CSS variables**: Defined in `globals.css` with both light and dark themes using HSL color format

The theme toggle is available in the user profile under "Reading Preferences > Dark Mode". The system respects the user's system preference by default and allows manual switching between light and dark modes.

### Brand Colors

Our app uses HSL color values defined in `globals.css` rather than the OKLCH values that were originally planned. The HSL approach was chosen for better compatibility and simpler implementation, and the theme looks good with these values.

The original OKLCH color tokens were removed from the project as they weren't needed and to avoid confusion with multiple theme definitions.

### Authentication Architecture

We've implemented a decoupled authentication approach that leverages the strengths of both frontend and backend frameworks:

1. **Frontend Authentication Flow (NextAuth)**
   - Handles user authentication via Google, Apple, and passwordless email magic links
   - Manages authentication state using JWT tokens and Prisma adapter
   - Provides seamless login experience without redirects between systems

2. **Backend User Management (Django)**
   - Maintains primary user models and permissions through Django's robust auth system
   - Synchronizes with frontend auth through API integration
   - Handles authorization for protected API endpoints

3. **Integration Mechanism**
   - On successful frontend authentication, a corresponding Django user is created/updated
   - NextAuth session includes reference to Django user ID
   - API requests include NextAuth tokens that Django validates
   - User permissions and data access controlled by Django backend

This hybrid approach provides several benefits:
- Simplified OAuth flows with NextAuth's built-in providers
- Robust backend access control with Django's permission system
- Improved user experience with client-side auth handling
- Maintainable architecture that separates concerns appropriately

In production, token validation uses shared secrets or public keys to ensure security between systems.
